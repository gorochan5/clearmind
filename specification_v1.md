# Doggy — Product and Engineering Specification

**Document:** Specification v1.0  
**Status:** Implementation baseline  
**Product:** Doggy, a native desktop live Markdown editor  
**Target repository:** `doggy`  
**Target framework:** iced dependency configured in the repository's `Cargo.toml`

## 1. Purpose and audience

Doggy is a small desktop application for editing GitHub Flavored Markdown (GFM) source while viewing a live rendered preview. The initial release focuses on a fast, readable two-pane authoring experience and a lean native application. It does not include file management, publishing, or collaboration features.

This document is the implementation brief for the engineer building the initial release. It defines product behavior, implementation boundaries, visual direction, and completion criteria. The deliverable for this task is the application implementation; this specification is not itself requesting those source files as output.

## 2. Goals

- Provide a native desktop Markdown editor with an immediately useful preview.
- Keep editor state and parsed preview state in the application model so rendering does not parse Markdown on every view call.
- Match the repository’s pinned iced API and dependency graph.
- Keep the implementation self-contained in `src/main.rs` and avoid unnecessary dependencies.
- Start with sample content that demonstrates the supported Markdown presentation.

## 3. Non-goals

The initial release does not require:

- Opening, saving, or managing files.
- Exporting HTML, PDF, or other formats.
- Network access, accounts, synchronization, or collaboration.
- A WebView or HTML rendering engine.
- Custom Markdown parsing or GFM extensions beyond what the pinned iced Markdown widget supports.
- A plugin system, settings screen, or theme selector.
- Guaranteed syntax highlighting unless the feature is supported by the pinned iced version and can be enabled without changing the repository’s iced pin.

## 4. Repository and dependency constraints

1. Read and follow the repository’s `AGENTS.md` instructions.
2. The existing iced dependency declaration in `Cargo.toml` is authoritative. This checkout currently has no `Cargo.lock`; do not describe the dependency as lockfile-reproducible. Do not downgrade to iced 0.13/0.14 or change the iced git source, branch, or version requirement. A lockfile may be generated by Cargo as part of normal build verification, but it is not a product deliverable unless repository policy requires it.
3. Treat `docs/iced/` as the authoritative API reference for the pinned iced revision. Consult the relevant pages before using iced types, widgets, traits, or functions. Follow re-export stubs to canonical documentation pages.
4. Do not edit any file under `docs/iced/`.
5. Do not add dependencies unless explicitly required. Feature flags may be adjusted on the existing iced dependency when supported by the pinned source. Preserve unrelated dependencies and project settings; do not replace the manifest wholesale.
6. Use only native iced widgets for the editor and preview. Do not use WebViews, Tauri, Wry, or HTML engines.

## 5. User experience

### 5.1 Startup

On launch, Doggy displays its main editor window populated with a Markdown sample. The sample is also the initial editor content, so the preview is populated without requiring user input.

Set the native window title to `Doggy`. Use a practical desktop default size and enforce a minimum size that keeps both panes usable. The layout remains side by side when resized; if the available width becomes too narrow, panes may become correspondingly narrow rather than switching to a different navigation mode.

The sample must demonstrate:

- H1, H2, and H3 headings.
- A blockquote.
- Ordered and unordered lists.
- Inline code.
- A clickable link.
- A Rust fenced code block.

### 5.2 Editing and preview

The main window is divided into two equally sized panes. The left pane contains the Markdown source editor; the right pane contains the rendered preview. A subtle vertical rule separates them.

When the user performs an editor action that changes the document—including typing, deletion, paste, undo, or redo—Doggy updates the Markdown source and refreshes the parsed preview. Non-editing editor actions such as cursor movement or selection changes must not trigger Markdown parsing. The preview should correspond to the current source after each editing action is processed. Empty or syntactically incomplete Markdown remains editable and should render using the parser's normal behavior without crashing.

Both panes must support scrolling when their content exceeds the visible area. The source pane must use a monospace font. The preview must be rendered using iced’s native Markdown widget.

### 5.3 Links

Links in the preview must be interactive using the pinned iced Markdown API. On click, Doggy logs the clicked URL with `tracing` at info level and handles the event without panicking. Opening the system browser is out of scope for this release.

### 5.4 Markdown dialect

The rendering dialect is the Markdown syntax supported by the pinned iced Markdown parser. The product intent is GFM-style authoring, but the implementation must not claim support for GFM extensions (such as tables, task lists, or strikethrough) unless those features are documented and supported by the pinned parser. The required sample syntax in §5.1 is mandatory; other extensions are best-effort and are not acceptance blockers.

## 6. Functional requirements

### FR-1 — Application entry point

Use the modern `iced::application(title, update, view)` builder API supported by the pinned version. Use `iced::Task` where the API requires an asynchronous task. Do not implement the deprecated `Application` trait or use `Command`.

### FR-2 — Application state

Define an application state type named `Doggy`. It must own:

- The `iced::widget::text_editor::Content` for the Markdown source.
- A `Vec<iced::widget::markdown::Item>` containing the parsed preview representation.

Additional state may be added only when needed by the documented iced API or a required interaction.

### FR-3 — Parse-on-edit update flow

Handle text editor actions in `update`. When an action modifies the source, apply it to the editor content and regenerate the parsed Markdown items from the resulting source. Use the pinned API’s documented edit predicate or equivalent documented action handling.

Do not parse Markdown in `view`. The view function must consume the already-parsed preview items.

### FR-4 — Split-pane layout

Construct a horizontal layout with:

1. A source editor pane using equal fill-portion sizing.
2. A one-pixel vertical divider using the pinned API’s documented rule/divider widget.
3. A rendered Markdown pane using equal fill-portion sizing.

Wrap the editor and preview content in scrollable containers, using the pinned API’s idiomatic composition. Keep pane widths balanced around the divider.

### FR-5 — Markdown rendering

Use `iced::widget::markdown::parse` to build the stored item vector and the documented `markdown::view` API to render it. Configure Markdown settings and theme using APIs available in the pinned version.

### FR-6 — Link events

Map Markdown link events into the application message type and handle them in `update`. At minimum, emit a `tracing` log entry containing the clicked URL.

### FR-7 — Theme and visual style

Use iced’s documented custom theme APIs where supported by the pinned version. Apply the following GitHub Dark-inspired palette:

| Role | Hex | RGB |
| --- | --- | --- |
| Main canvas | `#0d1117` | `(13, 17, 23)` |
| Secondary surface / editor and code background | `#161b22` | `(22, 27, 34)` |
| Borders and rules | `#30363d` | `(48, 54, 61)` |
| Primary text | `#c9d1d9` | `(201, 209, 217)` |
| Links and accents | `#58a6ff` | `(88, 166, 255)` |

Use documented widget style closures or equivalent APIs to apply the palette to the editor, scrollbars, divider, and other visible controls where practical. Do not rely on undocumented styling behavior.

### FR-8 — Syntax highlighting

If supported by the pinned iced API, enable the Markdown highlighter feature on the existing iced dependency and configure a documented dark syntax theme. Do not change the iced source, branch, or version requirement to obtain this capability. Code blocks without a language identifier or with an unsupported language must still render as readable code without a panic. If highlighting or a named theme is unavailable, retain readable fenced-code rendering and document the limitation in the implementation summary.

### FR-9 — Error handling and telemetry

Keep error handling appropriate to the small application. Use existing `anyhow` and `tracing` dependencies where useful; do not introduce logging initialization or error plumbing that is not needed. Link clicks must be handled safely. Initialization failures should be returned or logged through the application entry point using the error type required by iced; do not silently panic for recoverable setup failures.

## 7. Implementation and deliverables

The implementation deliverables are:

- `Cargo.toml`, updated only as needed to enable required features or configure the requested release profile while preserving the pinned iced dependency and existing project conventions.
- `src/main.rs`, containing the complete application implementation.

The implementation must be idiomatic, self-contained, and free of placeholders, `todo!()`, and omitted code blocks. Keep application logic in `src/main.rs`; do not split the implementation into additional source modules for this initial version. Modify only `src/main.rs` and the necessary iced feature/profile entries in `Cargo.toml`, except where a build requirement demonstrates another change is necessary; explain any additional file changes.

If a lean standalone Windows executable is configured, use the requested release profile settings unless repository constraints require otherwise:

```toml
[profile.release]
lto = true
strip = true
codegen-units = 1
opt-level = 3
```

Do not remove or rewrite unrelated dependencies without justification.

## 8. Acceptance criteria

The implementation is complete when all of the following are true:

1. The application uses the iced version already pinned by the repository.
2. The entry point uses the documented application builder and does not use the deprecated `Application` trait or `Command`.
3. The launch window shows both the source editor and rendered sample preview.
4. The source editor is on the left, the preview is on the right, both panes are balanced, and a one-pixel divider separates them.
5. Both panes can scroll independently when their content overflows.
6. The editor uses a monospace font.
7. Editing the source refreshes the preview, while Markdown parsing is absent from the view function and only runs for modifying editor actions.
8. Preview links produce a handled application message and are logged or opened without a panic.
9. The sample includes every element listed in §5.1.
10. The custom dark palette is applied through documented iced theming and styling APIs to the extent supported by the pinned version.
11. Syntax highlighting is configured when available without changing the iced pin; otherwise fenced code remains readable and the limitation is stated.
12. The changed iced APIs were checked against the local `docs/iced/` documentation, and the implementation summary names the documentation paths consulted.
13. `cargo check` completes successfully after the implementation changes.
14. No files under `docs/iced/` are modified, and no unrequested dependencies are added.

## 9. Verification and reporting

After implementing the application, run `cargo check` and resolve compilation errors. Do not add or run additional tests unless requested. The implementation review should include this manual smoke checklist:

1. Launch Doggy and confirm the sample and preview appear.
2. Type, delete, paste, undo, and redo Markdown; confirm the preview follows the source.
3. Move the cursor without editing; confirm the preview remains stable.
4. Click a preview link; confirm its URL is logged and the application remains responsive.
5. Resize the window and confirm the panes remain visible and balanced.
6. Add enough content to each pane to confirm scrolling works.

In the completion report, summarize the files changed, note any iced API or feature limitation, report the `cargo check` result, and cite the local iced documentation paths used for API decisions. If a Windows executable is part of the requested build, also report the target and build result; do not imply cross-compilation was verified unless it was actually run.

## 10. Implementation notes and open points

- “GitHub Dark-inspired” describes the target palette and overall contrast; exact parity with GitHub’s Markdown CSS is not required because native iced widgets render the content.
- The Markdown parser’s exact GFM feature coverage is determined by the pinned iced implementation. Do not claim support for extensions that are not documented or implemented there.
- Native font availability varies by operating system. Use iced’s documented monospace font option rather than bundling a font unless a later requirement requests one.
- Keep any unavoidable implementation limitation explicit in the final implementation report rather than adding speculative dependencies or changing the pinned iced revision.
